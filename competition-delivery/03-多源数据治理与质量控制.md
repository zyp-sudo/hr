## 1. 数据治理总体框架

### 1.1 治理目标

本项目的数据治理不是一次性清洗，而是一个**贯穿采集→ETL→图谱→应用的四层联动质控体系**：

```text
采集层                 ETL 层               图谱层              应用层
┌──────────┐        ┌──────────┐        ┌──────────┐        ┌──────────┐
│ 来源注册  │   →    │ 统一Schema│   →    │ 质量闸门  │   →    │ 联动影响  │
│ 去重规则  │        │ 12维评分  │        │ 边过滤    │        │ 可信度标记│
│ 海外防护  │        │ 技能标准化│        │ 重复去重  │        │ 匹配降权  │
│ 字段守恒  │        │ 岗位消歧  │        │ 版本管理  │        │ 建议分级  │
└──────────┘        └──────────┘        └──────────┘        └──────────┘
```

### 1.2 四层联动机制

核心设计原则：**质量评分不仅是一份报告，而且联动影响所有下游应用**。

| 层级 | 质控动作 | 联动影响 |
|------|----------|----------|
| 采集层 | 来源注册+去重+防护 | 不可信来源不入库 |
| ETL 层 | 12维扣分+等级分类 | C/D级记录进入问题池 |
| 图谱层 | 按质量过滤边 | 无技能命中→不生成requires边 |
| 应用层 | 质量分降权 | 低质量岗位降低匹配推荐可信度 |

## 2. 多源数据采集治理

### 2.1 数据源注册

当前注册的数据源共 6 个活跃来源，均在 `data/source_registry.csv` 中登记：

| 来源 | 类型 | 采集方式 | 记录贡献 | 信任权重 |
|------|------|----------|----------|----------|
| JobOnline 公共就业服务 | public_service | API 批量导入 | 50,000 | 0.7 |
| 美团招聘 | official_enterprise | 官网适配器 | 2,394 | 0.85 |
| 腾讯招聘 | official_enterprise_api | 官方API | 2,375 | 0.9 |
| 华为招聘 | official_enterprise | 官网适配器 | 378 | 0.85 |
| 国家大学生就业服务(NCSS) | public_service | API | 100 | 0.75 |
| 百度招聘 | official_enterprise | 官网适配器 | 20 | 0.8 |

**数据源分布分析**：
- JobOnline 公共就业服务占 ETL 总量的 90.5%（50,000/55,267），这是一个需要在报告中诚实地指出的数据分布特征。
- 企业官网来源合计约 5,167 条（腾讯+美团+华为+百度），占总量的 9.3%。
- 当前采集以中国公司为主，海外采集已显式禁用（`ALLOW_FOREIGN_SOURCES=0`）。

### 2.2 采集管道治理规则

| 规则 | 实现方式 | 目的 |
|------|----------|------|
| 来源注册 | `data/source_registry.csv` 登记所有来源 | 未注册来源不可入库 |
| 双键去重 | `source + postId` + `title+company+city+responsibility前300字` | 防止重复岗位污染统计 |
| 海外防护 | 默认 `ALLOW_FOREIGN_SOURCES=0` | 未经验证的海外数据不混入 |
| 增量合并 | merge 模式（非覆盖） | 保留历史采集成果 |
| 质量下限 | 未抽取到技能不生成图谱边 | 空壳岗位不污染图谱 |
| 字段守恒 | 必填字段缺失直接扣分 | 保证下游分析可用性 |
| 写入报告 | `collection_report.json` 记录每轮状态 | 采集过程可审计 |

### 2.3 采集报告审计

每轮采集运行后，`data/collection_report.json` 记录：

```json
{
  "write_mode": "merge",
  "existing_records_before_run": <运行前记录数>,
  "new_records_this_run": <本轮新增>,
  "actual_records": <合并去重后总量>,
  "region_counts": { "china": <数>, "foreign": 0 },
  "source_counts": { ... },
  "gap": <与目标的差距>
}
```

关键声明（来自 collection_report.json 原文）：
> "The pipeline never duplicates postings just to hit 100k."

### 3.2 数据质量评分体系

**评分模型**：100 分起始，12 项缺陷扣分。

| 序号 | 缺陷类型 | 扣分 | 影响说明 |
|------|----------|------|----------|
| 1 | 缺岗位名 (missing_title) | -25 | 核心标识缺失，无法参与匹配 |
| 2 | 缺来源URL (missing_source_url) | -15 | 无法验证数据真实性 |
| 3 | 缺采集时间 (missing_collected_at) | -15 | 无法判断数据时效 |
| 4 | 缺发布时间 (missing_published_at) | -10 | 无法用于演化分析 |
| 5 | 缺城市 (missing_city) | -5 | 影响地域分析 |
| 6 | 缺公司 (missing_company) | -5 | 影响企业维度分析 |
| 7 | 缺来源原始ID (missing_origin_record_id) | -5 | 影响溯源精度 |
| 8 | 职责文本过短 (short_responsibility) | -12 | 影响岗位画像和职责聚类 |
| 9 | 要求文本过短 (short_requirement) | -12 | 影响技能抽取和能力评分 |
| 10 | 未命中技能 (no_skill_hit) | -10 | 影响图谱边和匹配结果 |
| 11 | 内容重复 (duplicate_content) | -20 | 影响趋势热度和来源权重 |
| 12 | 未知来源 (unknown_source) | -10 | 数据可信度存疑 |

**等级划分**：

| 等级 | 分数区间 | 含义 | 处置方式 |
|------|----------|------|----------|
| A | ≥ 85 | 高质量 | 直接进入全部下游流程 |
| B | 70–84 | 可用 | 进入主流程，部分维度降权 |
| C | 55–69 | 需抽检 | 进入问题样本，标记审核 |
| D | < 55 | 限制入库 | 不进入核心指标口径 |

**库门规则（quality gate）**：

| 条件 | 门状态 |
|------|--------|
| score ≥ 95 且 issueRate < 8% 且 C/D级=0 | 可直接入库 |
| score ≥ 85 且 issueRate < 35% | 需抽检 |
| 其他 | 限制入库 |

### 3.3 技能标准化与能力维度映射

**标准化流水线**（`scripts/job_taxonomy.py`）：

```text

```

**10 大能力组**：

| 工程研发能力 | Java, Spring Boot, 微服务, 分布式 |

| 智能技术能力 | ML, Deep Learning, NLP, CV |
| 基础设施能力 | K8s, Terraform, 云原生, SRE |
| 工程质量能力 | 单元测试, 性能优化, Code Review |

| 通用能力 | 沟通, 学习能力, 团队协作 |

### 3.4 岗位实体消歧

**问题**：多源招聘数据中，同一岗位有大量变体名称。例如 "Java开发工程师"、"JAVA后台开发"、"Java 后端"、"高级Java工程师" 指的是同一个岗位族。

**方案**：`data/kg/role_aliases.csv` 包含 34,094 行消歧证据，每条记录包含：

| 字段 | 含义 | 示例 |
|------|------|------|
| alias | 原始JD中的岗位名 | "JAVA后台开发" |
| canonical_role_id | 规范岗位ID | "java-backend-engineer" |
| canonical_role | 规范岗位名 | "Java 后端工程师" |
| evidence_count | 证据出现次数 | 127 |

**去重效果**：MySQL 中 33,998 个不区分大小写的 distinct (alias, canonical_role_id) 对。Neo4j 保留所有 34,094 个区分大小写的原始别名。

## 4. 图谱层质量闸门

### 4.1 闸门规则

| 条件 | 动作 | 影响 |
|------|------|------|
| 无技能命中 (no_skill_hit) | 不生成 requires 边 | 该岗位不进入图谱关系 |
| 内容重复 (duplicate_content) | 仅保留一份用于趋势统计 | 避免重复JD抬高技能热度 |
| 质量等级为 C/D | 不进入核心指标口径 | 不参与匹配推荐的岗位池 |
| 质量等级为 A/B | 进入主流程 | 质量和匹配可信度正常 |

### 4.2 联动的下游应用影响

质量评分直接影响四大应用模块：

| 应用模块 | 影响机制 | 数据来源 |
|----------|----------|----------|
| 统一结果 (unified results) | A/B 级进入统一 Schema；低质记录隔离 | `unified_jobs.csv` |
| 能力图谱 (knowledge graph) | 无技能命中=不生成 requires 边 | `nodes.csv`, `edges.csv` |
| 动态演化 (evolution) | 重复 content_hash 只保留一份 | `skill_trends.csv` |
| 人岗匹配 (matching) | 低质量岗位降低匹配推荐可信度 | 匹配评分 |

## 5. 数据溯源全链路

### 5.1 溯源信息流

每条数据从源头到最终应用结论，保留完整溯源链：

```text
source_id → source_type → source_url → collected_at → published_at
  → origin_record_id → content_hash
  → quality_score → quality_level → quality_flags
  → normalized_skills → capability_dimensions
  → 图谱边（带权重和置信度）
  → 匹配证据（命中技能 + 来源引用）
```

### 5.2 可审计性

任何一条岗位记录的来源都可以通过以下路径回溯：

1. `record_id` → `source_id` → `source_registry.csv`（来源注册信息）
2. `content_hash` → 去重验证
3. `collected_at` → 采集时间线
4. `source_url` → 原始JD链接（如可用）

### 6.1 整体质量画像

| 指标 | 数值 | 说明 |
|------|------|------|
| ETL 统一岗位总量 | 55,267 条 | 多轮采集合并后的累计全量 |
| 技能证据条数 | 69,615 条 | 从JD文本中抽取的技能命中 |
| 数据来源数 | 6 个活跃来源 | 含公共就业平台和企业官网 |
| 岗位类别覆盖 | 10 类 | AI/后端/数据/产品/云/测试/设计/前端/安全/其他 |
| 学历字段覆盖率 | 61.32%（33,891条） | 仅提取显式学历词 |
| 薪资字段覆盖率 | 20.35%（11,246条） | 仅标准人民币月薪/年薪 |

### 6.2 字段级质量分析

**学历提取**：
- 非空：33,891 条（61.32%）
- 留空原因：JD 未提及学历、面议、或表述不规范（"博士优先"等不计入）
- 提取方式：保守规则，从 requirement/responsibility 中匹配显式学历关键词

**薪资提取**：
- 非空：11,246 条（20.35%）
- 留空原因：面议（占多数）、外币薪资、日时薪、没有周期的裸区间
- 提取方式：正则匹配人民币月薪/年薪区间

> **重要说明**：覆盖率 ≠ 抽取准确率。字段覆盖率反映的是源数据中该字段的可提取比例，而非提取结果的正确率。例如学历覆盖率 61.32% 表示 61.32% 的 JD 中可找到显式学历词，但未对提取结果做独立标注验证。

### 6.3 数据代表性局限

| 局限 | 说明 | 影响 |
|------|------|------|
| 单源占比过高 | JobOnline 占 90.5% | 公共就业平台数据的岗位描述可能比企业官网简略 |
| 企业官网有限 | 仅 5,167 条（9.3%） | 高端技术岗位代表性不足 |
| 地域偏倚 | 以中国岗位为主 | 海外岗位数据为空 |
| 时效性差异 | 不同来源的发布/更新频率不同 | 演化分析的时间粒度不均匀 |

## 7. 质量门禁与评测体系

### 7.1 确定性回归基准（165案例）

**性质**：规则模板自测。用 `scripts/job_taxonomy.py` 中硬编码规则生成输入，再验证同一套规则的输出。

| 测试类别 | 案例数 | 指标 | 数值 | 可信度 |
|----------|--------|------|------|--------|
| JD 技能抽取 | 80 | F1 | 1.0000 | 低——规则自测 |
| 岗位分类 | 45 | 准确率 | 1.0000 | 低——规则模板验证 |
| 简历字段 | 20 | 准确率 | 1.0000 | 低——规则自测 |
| 匹配决策 | 20 | 准确率 | 1.0000 | 低——二值阈值判定 |

> ⚠️ **不可作为生产准确率宣传**。满分 1.0 仅证明规则没有自相矛盾。

### 7.2 人工标注 Holdout（24案例）

| 指标 | 数值 | 案例数 | 标注情况 |
|------|------|--------|----------|
| 技能抽取 Precision | 0.7647 | 12 条 | 单标注者 |
| 技能抽取 Recall | 0.8667 | 12 条 | 单标注者 |
| 技能抽取 F1 | 0.8125 | 12 条 | 单标注者 |
| 岗位分类准确率 | 0.6667 | 12 条 | 单标注者 |

**分层分类表现**（12条）：
- AI: 0.50（2条中1条正确）
- 后端: 0.50（2条中1条正确）
- 数据: 0.00（1条，分类为"其他"）
- 前端: 0.00（1条，分类为"其他"）
- 其他各类: 1.00（各1条）

**已知局限**：
- 样本量极小（24条），统计误差大
- 单标注者，非双盲设计
- 岗位分类在小类上不可靠（数据0.0、前端0.0各仅1条样本）
- 文档自述："Small diagnostic holdout; expand with two independent domain annotators before production claims"

### 7.3 检索基准（4 Query Pool）

| 指标 | 数值 | Query数 | 标注方式 |
|------|------|---------|----------|
| Mean MRR@10 | 1.0000 | 4 | Pooled top-10, 单标注者 |
| Mean nDCG@10 | 0.9315 | 4 | Pooled top-10, 单标注者 |
| Mean Judged Coverage@10 | 1.0000 | 4 | 由pooling设计决定 |

**Query列表**："大模型推理"、"Java 后台"、"产品经理"、"游戏引擎"

**已知局限**：
- 仅4个query，覆盖极窄
- 单标注者，非双盲
- Judged coverage=100% 是因为只对top-10做标注（pooling），不是真实全库覆盖
- MRR=1.0意味着每个query的第一个结果都是相关——4个query均为精选案例

## 8. 未来治理方向

### 8.1 短期（比赛后1–2月）

1. 扩展 holdout 样本至 ≥ 200 条
2. 引入双人独立标注 + 双盲验证
3. 检索基准扩展至 ≥ 30 query，覆盖所有岗位类别
4. 生成并提交单元测试覆盖率报告（当前 pyproject.toml 目标 60%）
5. 学历和薪资字段提取做独立准确率评测

### 8.2 中期（比赛后3–6月）

1. 来源交叉验证：同一岗位在多个来源的描述一致性评分
2. 时间衰减评分：越新的JD权重越高
3. 无来源能力项自动标记为待审核
4. 大模型生成内容强制绑定 `sourceIds`
5. 重跑 `build_full_pipeline.py` 使仓库导出与 ETL 同步

### 8.3 长期

1. 重复JD聚类算法（语义级去重，非仅 content_hash）
2. 来源可信度动态调整（基于历史质量表现）
3. 数据漂移监控（月度质量报告趋势）
4. 自动修复建议（"该字段可从原始API响应中补充"）
