## 1. 问题定义

### 1.1 什么是"能力幻觉"

在本项目语境下，"幻觉"指大模型（或规则引擎）生成以下类型的虚假或不可验证信息：

| 幻觉类型 | 表现 | 危害 |
|----------|------|------|
| **技能幻觉** | 声称某岗位需要某技能，但所有来源JD中均未出现 | 求职者浪费时间学习不需要的技能 |
| **趋势幻觉** | 声称某技能"需求快速增长"，但缺乏时序数据支撑 | 企业和高校做出错误的培训/专业决策 |
| **匹配幻觉** | 声称候选人"完全匹配"某岗位，实际命中率很低 | 招聘方误筛合适的候选人 |
| **来源幻觉** | 生成结论无法回查到原始JD或数据文件 | 评审无法验证系统可信度 |

### 1.2 核心设计原则

> **"大模型输出必须有约束：生成结果必须经过来源回查、图谱事实校验和人工审核标记，避免能力幻觉。"**
> —— 《项目总设计文档》第2.5节

## 2. 幻觉防控三层架构

### 2.1 架构总览

```text
┌─────────────────────────────────────────────────────────────┐
│ 第三层：人工审核层 (Human Review Layer)                       │
│ · 低置信度结论标记 "待审核"                                   │
│ · 无来源能力项进入人工复核队列                                │
│ · 审核结果回写 → 更新可信度                                   │
└─────────────────────────────────────────────────────────────┘
                            ↑
┌─────────────────────────────────────────────────────────────┐
│ 第二层：图谱事实校验层 (Graph Fact Verification Layer)         │
│ · LLM 生成 → 图谱回查 → 找不到事实 → 降置信度                  │
│ · 生成结论绑定 sourceIds                                      │
│ · 无来源支撑标记                                               │
└─────────────────────────────────────────────────────────────┘
                            ↑
┌─────────────────────────────────────────────────────────────┐
│ 第一层：规则引擎约束层 (Rule Engine Constraint Layer)          │
│ · 确定性规则不可被 AI 覆盖                                    │
│ · 技能词典白名单过滤                                          │
│ · 空输入/无证据强制低分                                        │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 第一层：规则引擎约束（已实现）

**设计思路**：确定性规则是幻觉防控的第一道防线。AI 的分析只能解释规则结果，不能改写规则结果。

**已实现的约束机制**：

| 约束 | 实现方式 | 状态 |
|------|----------|------|
| 规则优先 | Java 匹配引擎先计算 ruleScore，AI 只能在此基础上分析 | ✅ 已实现 |
| 技能白名单 | 匹配仅使用 skill_aliases.csv 中注册的技能词 | ✅ 已实现 |
| 同义词归一 | K8s→Kubernetes，避免因写法不同遗漏真实技能 | ✅ 已实现 |
| 证据绑定 | matchedDetails 记录简历中命中的具体文本片段 | ✅ 已实现 |
| 空输入防御 | 简历为空时技能命中为空列表，不做模糊匹配 | ✅ 已实现 |
| 质量联动 | 低质量岗位（C/D级）降低匹配推荐可信度 | ✅ 已实现 |

**已识别的缺陷与改进方向**：

| 缺陷 | 表现 | 改进方案状态 |
|------|------|-------------|
| fallback 评分膨胀 | 空简历→78分（硬编码基准分） | ⚠️ 方案已文档化，待实施 |
| AI prompt 无校准 | LLM 未被要求逐项按证据打分 | ⚠️ 方案已文档化，待实施 |

### 2.3 第二层：图谱事实校验（部分实现）

**设计思路**：任何声称的岗位能力项，都应能在知识图谱中找到对应的节点和边，或标注为"待验证"。

**已实现的校验机制**：

| 校验 | 实现方式 | 状态 |
|------|----------|------|
| 图谱边过滤 | 无技能命中（no_skill_hit）的记录不生成 requires 边 | ✅ 已实现 |
| 重复去重 | 重复 content_hash 仅保留一份用于趋势统计 | ✅ 已实现 |
| AI context 注入 | Java AI hook 将图谱事实作为上下文发给 LLM | ✅ 已实现 |
| DeepSeek 干运行 | 无 API Key 时输出 rule_based 结果，不伪造大模型输出 | ✅ 已实现 |
| source_id 追溯 | 每条 ETL 记录保留 source_id → source_url → content_hash 链 | ✅ 已实现 |

**待实现的校验机制**：

| 校验 | 设计 | 状态 |
|------|------|------|
| RAG 来源回查 | 轻量级确定性证据检索、来源引用和低置信度拦截已实现；完整 Chroma/LangChain/LLM 生产级 RAG 尚未完成 | ✅ 部分已实现 |
| 生成内容 sourceIds | LLM 输出的每个能力项必须绑定对应的图谱节点 ID | ⚠️ 开发中 |
| 交叉验证评分 | 同一技能在多个来源中的一致性 → 可信度加权 | ⚠️ 待验证 |

### 2.4 第三层：人工审核（已设计，待标注扩展）

**设计思路**：低置信度结论和无来源能力项必须进入人工审核队列。

**已实现的审核相关功能**：

| 功能 | 实现 | 状态 |
|------|------|------|
| 质量标记 | quality_flags 字段标记各类问题 | ✅ 已实现 |
| 审核状态字段 | 设计文档中定义了人工审核状态（待审核/已通过/已拒绝） | ✅ 已设计 |
| 问题样本 | dataQuality API 返回低分记录的 problemSamples | ✅ 已实现 |
| holdout 诊断 | 24条人工标注用于暴露规则盲区 | ✅ 已实现 |

**待完善的审核机制**：

| 需求 | 当前不足 | 计划 |
|------|----------|------|
| 双人标注 | 所有 holdout 仅1人标注 | 扩展到 ≥2 名独立标注者 |
| 争议仲裁 | 无仲裁流程 | 标注分歧 → 第三人仲裁 |
| 审核界面 | 无前端审核工作台 | TalentMatch 前端增加审核页面 |
| 标注规模 | 仅24条 holdout | 扩展到 ≥200 条分层样本 |

## 3. 大模型输出的安全约束

### 3.1 AI 分析 Hook 的约束设计

当启用 `MATCH_AI_ENABLED=true` 时，大模型（DeepSeek）会收到以下约束 prompt（来自 `MatchAiAnalyzer.java`）：

```text
System: "Ground every finding in the provided context."
        "不得编造候选人简历中没有的技能或经历。"
        "如果 ruleScore 为 0 或 resumeText 为空，明确标注'简历证据不足'。"

Context 注入:
  - ruleScore: 规则引擎计算的分数 (不可被 AI 覆盖)
  - matchedDetails: 简历中实际命中的技能证据
  - missingDetails: 确实缺失的技能
  - dimensions: 维度评分
  - requiredSkills: 目标岗位的技能要求（含来源和权重）
```

### 3.2 Dry-run 模式防护

当 `DEEPSEEK_API_KEY` 未配置时：
- DeepSeek 抽取脚本输出 `dry_run` / `rule_based` 结果
- 明确标注为非大模型输出
- 不伪造 AI 推理痕迹

### 3.3 已识别的 prompt 缺陷（待修复）

来自 `docs/score-calibration-proposal.md` 的诊断：

1. **fallback 函数硬编码 78 分基准**：`talentmatch/server.ts:87` → 空简历也能得 78 分
2. **LLM prompt 无校准锚点**：未要求"逐维度按证据打分"，未设置"无证据则 0 分"
3. **Java 后端 prompt 缺乏校准**：system prompt 只说了"Ground every finding"但未明确评分规则

**已文档化的修复方案**（P0→P2 优先级）详见 `docs/score-calibration-proposal.md`，当前状态为"待实施"。

## 4. 数据源头可信度管理

### 4.1 来源信任权重

每个数据源在注册时分配信任权重（trustWeight，0–1），用于后续分析的可信度加权：

| 来源 | 信任权重 | 依据 |
|------|----------|------|
| 腾讯招聘（官方API） | 0.9 | 企业官方发布，结构化数据 |
| 美团招聘（官网） | 0.85 | 企业官方发布 |
| 华为招聘（官网） | 0.85 | 企业官方发布 |
| 百度招聘（官网） | 0.8 | 企业官方发布 |
| 国家大学生就业服务 | 0.75 | 政府公共服务平台 |
| JobOnline 公共就业服务 | 0.7 | 公共服务平台，数据量大但描述简略 |

### 4.2 来源质量联动

质量评分按来源聚合后，联动影响下游：

```text
来源评分 < 阈值
  → 该来源的新岗位标记 "限制入库"
  → 该来源的技能证据降低加权权重
  → 该来源的趋势数据标注来源可信度警告
```
